# riscv64 vs libjpeg-turbo 3.2.0 RVV — emulator measurement (P4-134, issue #465)

**Purpose.** P4-134 criterion 1 asks for a measurement of our decode and
encode against libjpeg-turbo **3.2.0** on riscv64, where upstream now ships
RISC-V Vector (RVV) kernels and we dispatch scalar. No RVV hardware was
available; this run uses the only vector-capable emulator at hand and
records, first of all, **what the emulator can and cannot say**.

**Headline.** Under `qemu-riscv64` the RVV build of C libjpeg-turbo runs
**3–5× slower than C's own scalar path** on the same binary (below). QEMU's
TCG executes each vector instruction through a helper loop, so vector code
pays an emulation tax scalar code does not — the asymmetry P4-78 predicted
for ARMv7 NEON, now measured. An emulator therefore **cannot stand in for
the hardware measurement**: every "ours vs C-RVV" ratio it produces has the
wrong sign. What it *can* measure is the scalar-vs-scalar pair against
3.2.0 (`JSIMD_FORCENONE=1`), which is the P4-60 quantity, and whether a
`+v` build of ours vectorises at all. Both are recorded here; the hardware
gap stays **inferred**, and the inference is stated as such in
`docs/last_mile/phase4.md` (P4-134).

## Environment

- Host: Apple aarch64, Docker Desktop 29.7.2 (`linux/arm64` VM, 8 vCPU,
  8 GiB). Build container `debian:trixie`; everything below was
  **cross-compiled natively** and executed under user-mode QEMU, so the
  compiler is never emulated and the CPU model is under our control.
- Emulator: `qemu-riscv64-static` **10.0.11** (Debian
  `1:10.0.11+ds-0+deb13u1`), `-cpu rv64,v=true,vlen=128` unless stated,
  `-L /usr/riscv64-linux-gnu`. Scalar controls: `JSIMD_FORCENONE=1` (C's
  own runtime switch, `simd/jsimd.c:95`) and `-cpu rv64,v=false` (the V bit
  absent from `AT_HWCAP`, so C's `jsimdcpu.c` probe falls back).
- C: libjpeg-turbo **3.2.0** from `references/libjpeg-turbo` @ `c85e6b9`,
  `riscv64-linux-gnu-gcc` 14.2.0-19, CMake 3.31.6, `-DCMAKE_BUILD_TYPE=Release
  -DWITH_SIMD=1 -DENABLE_SHARED=0` (`HAVE_RVV - Success`,
  `SIMD extensions: RISCV64`). Two `tjbench` legs, both in-process,
  megapixels/s: **decode** = `tjbench-static <fixture>.jpg -rgb -nowrite
  -quiet -benchtime 4 -warmup 1` (decompress-only mode, `src/tjbench.c:1065-1071`,
  which decodes the fixture itself); **encode** = `tjbench-static <ppm> 95
  -subsamp 420 -rgb -nowrite -quiet -benchtime 4 -warmup 1` (RGB → baseline
  4:2:0 q95), where `<ppm>` is host `djpeg` 3.1.4.1 output of the same
  fixture. A first pass had taken the decode figure from the compress leg's
  own decompress column; review caught that `fullTest` decodes the q95
  stream it just produced (`tjbench.c:599`) — ~2× the entropy-coded bytes
  of the q75 640×480 fixture — and that pass was discarded.
- Ours: `libjpeg-turbo-rs` at this commit, rustc **1.98.0** (LLVM 22.1.8),
  `--release` (`lto = true`), target `riscv64gc-unknown-linux-gnu`, linker
  `riscv64-linux-gnu-gcc`. Harness: `examples/bench_p4134_riscv64.rs` —
  the same two operations (`decompress_into` the fixture to RGB with the
  destination allocated once outside the timed region, as `tjbench` does;
  `compress` RGB → 4:2:0 q95, `IsLow`, which is `tjbench`'s default DCT),
  in-process medians after one discarded warmup iteration, 7 runs (15
  where stated). Known residual asymmetries, stated in the example's header:
  our encode allocates its output per iteration where `tjbench`
  pre-allocates, and we report a median where `tjbench` reports a warmed
  mean. The P4-60 probe `examples/bench_scalar_p460.rs` (decode only, no
  warmup, `decompress()` allocating per run) was run alongside for
  continuity with `riscv64_scalar_2026-07-27.md`.
- Inputs: `tests/fixtures/photo_640x480_420.jpg` (q75),
  `tests/fixtures/photo_1920x1080_420.jpg` (q90).

**Absolute times are emulated and meaningless.** Only ratios within one
configuration family are data, and even those carry the noise band below.

## Mechanism proofs (the runs measure what they claim to)

| check | result |
| --- | --- |
| RVV code present in the C tools (`objdump -d`, gcc-built, arch attribute `v1p0`) | `vsetvli` ×324, `vle*/vse*` ×244 in each of `djpeg`, `cjpeg`, `tjbench` |
| RVV code **executed** (`qemu -d in_asm`, translated blocks, `djpeg` 640×480, V on) | `vsetvli` blocks 57, `vle*/vse*` 38 |
| same with `JSIMD_FORCENONE=1` | 0 vector blocks |
| same with `-cpu rv64,v=false` | 0 vector blocks |
| RVV vs scalar `djpeg` output | byte-identical (`cmp`) |
| our baseline build (`riscv64gc`, no flags) | 0 vector blocks translated |
| our `-C target-feature=+v` build, `bench_p4134_riscv64 1` | `vsetvli`/`vsetivli` blocks 284, `vle*/vse*` 337 |

Note for anyone repeating this: binutils `objdump` **does not decode**
vector instructions in rustc-built binaries (they print as `.4byte`/unknown
— 9,344 of them in the `+v` build), so count vector ops in the pre-LTO
assembly (`cargo rustc --lib -- --emit=asm`) or in QEMU's `in_asm` log,
never in `objdump` output of the Rust binary.

## C libjpeg-turbo 3.2.0 under QEMU: RVV is slower than scalar

`tjbench`, megapixels/s (higher is better). Decode = decompress-only leg
on the fixture; encode = q95 4:2:0 compress leg from the PPM.

| fixture | configuration | decode | encode |
| --- | --- | ---: | ---: |
| 640×480 | RVV (`v=true,vlen=128`) | 8.350 | 7.645 |
| 640×480 | RVV (`v=true,vlen=256`), encode leg only | — | 8.190 |
| 640×480 | scalar (`JSIMD_FORCENONE=1`) | 39.98 | 29.00 |
| 640×480 | scalar (`v=false`) | 40.72 | 29.93 |
| 1920×1080 | RVV (`v=true,vlen=128`) | 6.873 | 6.452 |
| 1920×1080 | scalar (`JSIMD_FORCENONE=1`) | 21.84 | 21.06 |
| 1920×1080 | scalar (`v=false`) | 22.98 | 22.03 |

**C-RVV / C-scalar under QEMU: 0.21× decode / 0.26× encode at 640×480,
0.31× / 0.31× at 1080p.** On the Ky X1 upstream reports the same kernels
at **+48–180 % decompress, +149–246 % compress** (3.2 beta1 ChangeLog note
6). The emulator inverts a 1.5–3.5× hardware win into a 3–5× loss, and
doubling VLEN barely moves it — the cost is per vector instruction, not per
element. This is the finding that gates everything else: **no ratio
involving the RVV build measured here says anything about hardware.**

## Scalar vs scalar against 3.2.0 (the P4-60 quantity, re-measured)

Ours (baseline scalar build) vs C with `JSIMD_FORCENONE=1`, same emulator.
Ours is the range over three back-to-back 7-run medians plus one 15-run
median; the spread is under 10 % on every row (a first-pass harness without
the warmup iteration and with a per-run output allocation had spread to
25 % and disagreed with the P4-60 probe by ~1.4× at 640×480 — both effects
vanished once the harness matched `tjbench`'s shape).

Raw medians, µs: `bench_p4134_riscv64` 640×480 decode 11,255 / 11,438 /
11,340 (15-run: 11,206), encode 19,162 / 19,435 / 20,571 (15-run: 18,857);
1080p decode 102,163 / 102,197 / 102,529 (15-run: 102,662), encode 171,061 /

Read this as: **decode sits at the P4-60 07-28 position (1.1–1.7× there,

since), encode is a new data point at ~1.7–1.9× — and both are the scalar
deficit only.** Both encode rows carry the per-iteration allocation bias
noted above, so they are upper bounds on the deficit, not exact.

## Does a `+v` build of ours vectorise? Yes — but not the kernels

rustc 1.98.0 accepts `-C target-feature=+v` on stable with a warning
(`unstable feature specified for -Ctarget-feature: v`) and honours it;
`-C target-cpu=sifive-x280` / `sifive-p670` / `spacemit-x60` enable V with
no warning at all. Vector ops in the crate's own pre-LTO assembly, `+v`:

| where | vector instructions |
| --- | ---: |
| whole `libjpeg_turbo_rs` lib (267 functions) | **7,930** (`vsetvli` 2,118) |
| `decode::pipeline::output::Decoder::decode_image_inner` | 815 |
| `decode::pipeline::arithmetic::Decoder::decode_arithmetic_planes` | 594 |
| `encode::pipeline_impl::quant_divisors::scale_quant_for_fdct` | 79 |
| `api::quantize::quantize` | 44 |
| `decode::idct::idct_8x8` (+ `idct_8x8_12bit`) | **9** |
| `decode::upsample::fancy_h2v2_row` | **0** |
| `decode::color::ycbcr_to_rgb_row` / `simd::scalar::scalar_ycbcr_to_rgb_row` | **0** |
| `encode::color::rgb_to_ycbcr_row` / `simd::scalar::scalar_rgb_to_ycbcr_row_enc` | **0** |

The vectoriser finds copy/fill/setup loops in the pipeline plumbing and
essentially nothing in the four kernels that carry the pixels — the
opposite of the ARMv7 `+neon` result (`armv7_autovec_2026-07-30.md`:
`idct_8x8` 0 → 270, colour 0 → 140, upsample 0 → 232). The table-driven
colour convert is a gather, the IDCT's clamp/rounding chains do not SLP on
LLVM's RISC-V cost model, and the upsample row is a sliding 3-tap with
per-edge special cases. So option (D) of P4-78 — "enable the feature and
let the compiler vectorise" — has **no kernel-level win to offer on
riscv64 even in principle** with the kernels in their current shape.

For completeness the `+v` build was also timed (same emulator, same
harness): decode 640×480 69,163 µs, 1080p 488,550 µs; encode 80,089 /
560,829 µs — **4–6× slower than our own scalar build**, i.e. the same
emulation tax C's RVV pays, on 7,930 instructions that do not touch the hot
loops. That is an emulator artefact, not a statement about hardware; it is
recorded so nobody re-runs it expecting a signal. The `spacemit-x60`-tuned
build SIGILLs on QEMU's generic `rv64` model at both `vlen=128` and
`vlen=256` and was not measured.

## Toolchain status for criterion 3 (measured on rustc 1.98.0 stable)

| capability | status |
| --- | --- |
| `#[target_feature(enable = "v")]` | **unstable** — `error[E0658]: the target feature v is currently unstable` |
| RVV intrinsics in `core::arch::riscv64` | **none exist** (`E0425` on `vsetvli`; stdarch ships no vector intrinsics for RISC-V) |
| `std::arch::is_riscv_feature_detected!("v")` | **unstable** — `stdarch_riscv_feature_detection`, tracking issue rust-lang/rust#111192 |
| `-C target-feature=+v` | accepted with a warning, honoured by codegen (table above) |
| `-C target-cpu=<V-capable cpu>` | accepted silently, enables V (compile-time, SIGILL on non-V cores) |
| `core::arch::asm!` on riscv64 | stable |
| C 3.2.0 runtime detection to mirror | `AT_HWCAP` bit `V` + `riscv_hwprobe` syscall (`simd/riscv64/jsimdcpu.c:44-86`) |

## Verdict

- **Criterion 1 is satisfied only in the letter.** The emulator run proves
  the RVV kernels build, dispatch and execute for 3.2.0, and re-measures the
  scalar-vs-scalar pair (decode ~1.1–1.5×, encode ~1.7–1.9× behind C's
  scalar, spread under 10 %). It **cannot** produce the ours-vs-C-RVV number
  the criterion is for, because QEMU makes vector code slower than scalar.
  That number needs an RVV 1.0 board; until one is available the hardware
  gap stays an inference: composing the scalar deficit with upstream's
  reported RVV win (decode 1.1–1.5 × 1.48–2.80 = **1.6–4.2×**; encode
  1.7–1.9 × 2.49–3.46 = **4.2–6.6×**) puts us at **roughly 1.5–4× slower
  decode and 4–7× slower encode on RVV hardware** — the band quoted in
  P4-134, and an inference, not a measurement.
- **The scope decision is "defer"**: intrinsics do not exist, the target
  feature and runtime detection are unstable, auto-vectorisation reaches
  none of the kernels, and hand-written `asm!` kernels would be an
  unmeasurable investment until there is hardware to measure them on. The
  reopen trigger is recorded in P4-134.

**Status: recorded, not `keep`/`discard`** — this is a measurement, not an
optimisation attempt; no code path changed. `bench_p4134_riscv64` stays in
`examples/` so the hardware run, when it happens, uses the same harness.
