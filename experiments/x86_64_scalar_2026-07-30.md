# x86_64 scalar-vs-scalar decode: ours vs C (2026-07-30)

Run while answering [#424](https://github.com/developer0hye/libjpeg-turbo-rs/issues/424)
(ARMv7 performance) to test the load-bearing half of P4-78's estimate: the
claim that **our scalar kernels are 1.12-1.72x slower than C's scalar
kernels**, which until now rested on a single measurement on one ISA
(`riscv64_scalar_2026-07-27.md`, under emulation).

**Headline: the x86_64 numbers do not transfer, and the reason is the
finding.** Our decode with `JSIMD_FORCENONE=1` measures **0.80x at 640x480
and 0.89x at 1080p** of C's, i.e. parity-or-faster rather than the
1.12-1.72x *slower* seen on riscv64 — but `objdump` shows why, and it is not
a scalar-code win: **`decode::idct::idct_8x8` contains 162 packed-integer
SIMD instructions in the x86_64 build.** LLVM auto-vectorises it, because
SSE2 is baseline in the x86_64 ABI. `JSIMD_FORCENONE=1` disables our
*hand-written* kernels, not the compiler's vectoriser.

So this run does **not** refute P4-78's estimate, and it must not be quoted
as "our scalar path is fine". What it establishes is narrower and still
useful:

1. **x86_64 is unusable as an ARMv7 proxy** for scalar work. Any future
   "scalar" experiment on this host measures partly-vectorised code.
   `riscv64_scalar_2026-07-27.md` stays the only genuinely-scalar
   ours-vs-C datapoint.
2. **C's SIMD win on this CPU is ~1.5x**, not the 2-6x upstream headline
   (see the ratio table) — measured on decode only, where that headline
   covers the whole library including encode.
3. The colour kernel is *not* auto-vectorised (0 packed instructions in
   `ycbcr_to_rgb_row` — it is table-driven byte gathers), so the P4-60
   table-driven form is genuinely scalar on every target.

| Pinning | `taskset -c 0` on every measured command |

**Two environment caveats that matter.** (1) A U-series hybrid laptop CPU
with no `scaling_governor` / `no_turbo` control from WSL violates the
stable-clock rule in `CLAUDE.md`; repeat spreads below are ~1-2%, but no
absolute number here should be compared against a differently-clocked run.
(2) C is **2.1.5, not the project's 3.1.4.1 oracle** — installing the
official deb was blocked in this environment. 3.x carries decode
improvements over 2.1.x, so this biases **in our favour**.

## Method

`djpeg` is a process, so a single decode is far below `/usr/bin/time`'s
10 ms resolution. Each configuration is therefore a **100-iteration loop**
timed as a whole, with two corrections:

1. **Process startup**, measured the same way on a 16x16 fixture:
   0.117 s / 100 = **1.17 ms per invocation** (reps: 0.117, 0.126 s).
2. **Output-write cost**, which the 16x16 baseline cannot capture because it
   scales with image size. Bounded with `dd` writing the decoded byte count
   to `/dev/null`, minus `dd`'s own spawn cost (0.129 s / 100):
   6,220,800 B → (0.388-0.129)/100 = **2.59 ms**; 921,600 B →
   (0.154-0.129)/100 = **0.25 ms**.

Our side needs neither correction: `examples/bench_scalar_p460` reports
in-process medians (15 runs at 640x480, 7 at 1080p).

Both sides forced scalar with `JSIMD_FORCENONE=1`, which libjpeg-turbo and
our `simd::detect()` both honour.

## Reading these honestly

**Every uncorrected bias still favours us**, so the scalar ratios are a
lower bound on our time, i.e. the true figure is somewhat *worse* than
0.80x/0.89x: `djpeg` also pays per-invocation allocation and teardown for a
full-size image (the 16x16 baseline does not include it), plus whatever PPM
row formatting costs beyond the raw copy `dd` models, while our bench
measures decode only. The defensible claim is therefore **"our scalar
decode is at rough parity with C's on x86_64"**, not "we are 20% faster".

The direction is nonetheless the opposite of the riscv64 result, and the
`objdump` check settled why on the first try — it was listed here as "the
next thing to run" and is now done:

```
objdump -d --demangle target/release/examples/bench_scalar_p460
  | awk '/decode::idct::idct_8x8/{f=1} f&&/^$/{f=0} f'
  | grep -cE 'punpck|packus|packss|paddw|paddsw|psubw|pmullw|pmaddwd|psrlw|psllw|pshuf'
  -> 162          # same pipeline over ycbcr_to_rgb_row -> 0
```

**Codegen, not algorithm.** The x86_64 scalar IDCT is auto-vectorised;
riscv64's is not (no V extension in that target's baseline). That fully
accounts for the reversal without needing any claim about our scalar code
quality, and it means the honest ARMv7 predictor remains the riscv64
number, since Rust's `armv7-unknown-linux-gnueabihf` does not enable NEON
in its baseline either.

## Consequences for P4-78 / #424

1. The 2-5x ARMv7 estimate stands as an estimate. Its scalar factor
   (riscv64, 1.12-1.72x) is unaffected by this run; its NEON factor is the
   part now in question, because C's measured SIMD win here is **~1.5x**
   against a 2-6x quoted envelope. If NEON on an in-order ARM core behaves
   like AVX2 on this out-of-order x86 core, the band's upper half is too
   pessimistic — but in-order cores typically gain *more* from SIMD than
   wide OoO cores do, so this is a reason to distrust the number, not to
   move it.
2. The methodological lesson is the durable one: **do not run scalar
   experiments for ARMv7 on x86_64.** For a target where the compiler will
   not vectorise, the two usable environments are riscv64 (as before) and
   `qemu-arm` on the armv7 target — the latter valid only for
   ours-before-vs-ours-after A/B, where the emulation tax is symmetric, and
   never for ours-vs-C-with-NEON.
3. QEMU has no cache model, so the P4-78 follow-up hypothesis about
   `LOOKUP_BITS = 10` costing 4 KB per Huffman table on a 32 KB L1D is
   **not testable in any environment available here** — it needs real ARM
   silicon or a cache-modelling simulator.
